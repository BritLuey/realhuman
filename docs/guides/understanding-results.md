# Understanding results

Every decision answers two plain questions, and the answers combine into one **label** you can filter on:

1. **Did we see evidence of automation?** → `botEvidence`: none, weak, moderate, strong or conclusive
2. **Did we see evidence of a real person?** → `humanEvidence`: none, some or strong

This page explains each field in a decision record and exactly how it's worked out.

## The fields at a glance

| Field | Example | Use it for |
|---|---|---|
| **`label`** | `human` | **Filtering your data.** Start here. |
| `botEvidence` | `none` | Seeing how strong the case for "bot" is |
| `humanEvidence` | `strong` | Seeing how strong the case for "human" is |
| `primaryReason` | `pointer_natural` | Explaining the label in one phrase, e.g. on a dashboard |
| `reasons` | `["pointer_natural", "keyboard_natural"]` | Every piece of evidence, for investigation |
| `realHuman` | `0.96` | Ranking sessions and drawing ROC curves. **Not a probability.** |
| `confidence` | `0.81` | How much evidence there was overall |
| `verdict` | `human` | A coarser version of `label`, kept for compatibility |
| `kind` | `human` | A guess at *what* is driving the session |

## The five labels

| Label | What it means | Typical example | In analytics |
|---|---|---|---|
| **`human`** | Real interaction was seen, and at most weak signs of automation | Moved the mouse naturally and typed | Keep |
| **`unverified`** | Nothing suspicious, but no interaction to confirm a person | Opened the page and left after a few seconds | Keep: almost always a real but brief visit |
| **`suspicious`** | Some signs of automation, but nothing conclusive | Software-rendered graphics (common on remote desktops); a window with no browser toolbar | Keep in totals; exclude from experiments and conversion analysis |
| **`bot`** | Strong or conclusive signs of automation | Headless browser, filled honeypot, scripted clicks | Exclude |
| **`verified_agent`** | An AI agent or crawler that proved its identity cryptographically | A signed request from an agent you trust | Your decision |

## How the label is decided

**Bot evidence decides `bot` and `suspicious`. If there isn't enough of it, human evidence decides between
`human` and `unverified`.**

| | No human evidence | Some or strong human evidence |
|---|---|---|
| **No or weak bot evidence** | `unverified` | `human` |
| **Moderate bot evidence** | `suspicious` | `suspicious` |
| **Strong or conclusive bot evidence** | `bot` | `bot` |

A self-identifying agent with a valid [Web Bot Auth](../glossary.md#web-bot-auth) signature is always
`verified_agent`.

Natural-looking movement never cancels out strong bot evidence: a sophisticated bot can fake mouse movement,
but it can't make a headless browser stop being headless.

## How bot evidence is determined

Each bot-leaning signal has a **weight**. The weights of all the signals seen are added up:

| Level | Rule |
|---|---|
| `conclusive` | Any **gate** fired (list below) |
| `strong` | Total weight **4 or more**, or any single signal of weight **3.5 or more** |
| `moderate` | Total weight **1.5 or more** |
| `weak` | Any bot-leaning signal at all, below 1.5 |
| `none` | No bot-leaning signals |

### Gates: conclusive on their own

| Reason | Title |
|---|---|
| `honeypot_filled` | Honeypot filled |
| `honeypot_trap_followed` | Trap link followed |
| `agent_canary_followed` | Followed hidden AI-agent instructions |
| `automation_markers` | Automation framework detected |
| `ua_bot` | Declared bot or headless browser (e.g. `curl`, `python-requests`, `HeadlessChrome`) |
| `nonce_invalid`, `nonce_expired`, `nonce_replayed` | Invalid, expired or replayed session token |
| `too_fast` | Manipulated clock |

### Weighted bot-leaning signals

| Reason | Weight | When it fires |
|---|---|---|
| `webdriver` | 4 | `navigator.webdriver` is true. Strong on its own. |
| `worker_mismatch` | 3 | The page and a Web Worker report different browser details or graphics |
| `ja4_non_browser` | 3, or 4.5 if listed in `ja4.nonBrowser` | The TLS connection offered no ALPN at all, as HTTP libraries do, while the user agent claims a browser. Not a gate, because some company proxies and security tools re-make connections this way. A fingerprint you've listed in `ja4.nonBrowser` is strong on its own |
| `ua_ja4_mismatch` | 3 | The TLS connection doesn't look like the claimed browser (old TLS, no SNI, HTTP/1.1 only, very few ciphers) |
| `renderer_platform_mismatch` | 3 | The graphics stack belongs to a different operating system than the browser claims, for example Linux graphics on a browser claiming to be Windows |
| `synthetic_events` | 3 | Most input events were generated by script, or a click landed on a hidden element |
| `ua_client_hints_mismatch` | 2.5 | The user agent contradicts the browser's Client Hints |
| `native_tamper` | 2.5 | Built-in browser functions on `navigator`, `screen` or `window` have been overwritten or wrapped |
| `sec_fetch_missing` | 2 | A modern browser didn't send the fetch-metadata headers it always sends |
| `feature_mismatch` | 2 | The browser lacks features its claimed version has |
| `form_too_fast` | 2 | A protected form was submitted faster than a person could fill it in |
| `headless_markers` | 1.2 per trait; 1.6 for `no_browser_ui`; 0.4 for `zero_outer_size`; at most 3 | Traits of headless browsers, such as a window with no browser UI (`no_browser_ui`) or a page exactly the size of the screen (`viewport_is_screen`). `zero_outer_size` is ignored on phones and tablets |
| `software_renderer` | 1.5 | Graphics are drawn in software, as on servers, but also remote desktops and VMs |
| `pointer_linear` | 1.5 | 10+ mouse moves, over 80% in perfectly straight lines, at near-constant speed |
| `keyboard_uniform` | 1.5 | 8+ key presses with almost perfectly even spacing |
| `pointer_teleport` | 1 | 3+ clicks, at least half of them far (>30 px) from where the pointer was |
| `click_dead_center` | 1 | 3+ clicks, at least half within 1 px of the exact centre of their targets |
| `timezone_mismatch` | 0.5 | The browser's time zone differs from its IP address's (VPN users trigger this too) |

**Privacy browsers.** If the browser is privacy-hardened (Brave, Tor, Firefox with resistFingerprinting), the
signals those browsers trigger on purpose are ignored: `ua_client_hints_mismatch`, `worker_mismatch`,
`feature_mismatch`, `native_tamper`, `software_renderer`, `renderer_platform_mismatch`, `timezone_mismatch` and
`headless_markers`.

**Examples:**

| What was seen | Total | Bot evidence |
|---|---|---|
| Nothing | 0 | none |
| VPN time-zone mismatch | 0.5 | weak |
| Software graphics | 1.5 | moderate |
| Window with no browser UI | 1.6 | moderate |
| Linux graphics on a browser claiming Windows | 3 | moderate |
| No ALPN (a company proxy, say) | 3 | moderate |
| No ALPN + missing fetch-metadata headers | 5 | strong |
| `navigator.webdriver` | 4 | strong (single signal ≥ 3.5) |
| Honeypot filled | – | conclusive |

## How human evidence is determined

| Reason | Weight | When it fires |
|---|---|---|
| `pointer_natural` | 1.5 | 15+ trusted mouse moves with varying speed (variation > 0.3), mostly curved paths (under 60% straight) and some turning |
| `keyboard_natural` | 1.2 | 6+ trusted key presses with uneven rhythm (gap variation ≥ 0.25) and varied key-hold times |
| `touch_natural` | 1.2 | 4+ trusted touches with varying contact size or pressure, or taps lasting over 30 ms |
| `scroll_natural` | 0.6 | 5+ scroll events with an irregular rhythm, not in identical fixed steps |

| Level | Rule |
|---|---|
| `strong` | Total weight **2 or more** (e.g. mouse + typing, or mouse + scrolling) |
| `some` | Any human-leaning signal |
| `none` | None of the above |

Visitors who only load a page and leave have no human evidence. That's why they're `unverified`, not `human`.

## `primaryReason`

The single reason that best explains the label:

| Label | Primary reason |
|---|---|
| `bot`, `suspicious` | The first gate if one fired, otherwise the heaviest bot-leaning signal |
| `human` | The heaviest human-leaning signal |
| `unverified` | `no_interaction` if the visitor didn't interact, `no_js` if the SDK never ran, otherwise the weak bot hint that was seen |
| `verified_agent` | `verified_agent_signature` |

It can be `null` when nothing notable was seen. Show it on dashboards with its title, for example
`REASONS[primaryReason].title` from `@realhuman/schema` gives "Natural mouse movement".

## The score (`realHuman`)

The score combines the same weights into one number between 0 and 1:

1. Start at **+0.4**, because most visitors who run JavaScript are people.
2. Add every weight: bot-leaning signals are negative, human-leaning signals positive. Each group is capped
   (environment at −6, network at −5, behaviour between −5 and +3.5), so one group can't dominate.
3. Squash the total into 0–1 with the logistic function.

| What was seen | Score |
|---|---|
| Nothing (page load only) | 0.60 |
| VPN time-zone mismatch only | 0.48 |
| Natural scrolling | 0.73 |
| Natural mouse movement | 0.87 |
| Natural mouse movement and typing | 0.96 |
| Software graphics only | 0.25 |
| Any gate | 0.02 |

**The score is not a probability.** The weights are expert estimates, not fitted to data, so 0.87 doesn't mean
"87% likely human". Use it to rank sessions, draw ROC curves, or compare engines. To filter, use the label.

## Other fields

- **`verdict`** follows the label: `human` → `human`; `unverified` and `suspicious` → `uncertain`;
  `bot` → `bot`; `verified_agent` → `verified_agent`.
- **`confidence`** (0–1) grows with the amount of evidence: about 0.15 with none, more with a TLS fingerprint
  and headers, more again with each kind of interaction, and more with strong bot evidence.
- **`kind`** guesses what's behind the session: `human`, `privacy_browser`, `automation` (driven browsers),
  `scraper` (headless or non-browser clients), `ai_agent`, `verified_agent`, `no_js` or `unknown`.

## Querying

```sql
-- Standard: remove bots from all reporting
WHERE label <> 'bot'

-- Strict: experiments, conversion rates, anything where a bot would distort the result
WHERE label IN ('human', 'unverified')

-- How clean is my traffic?
SELECT label, COUNT(*) FROM latest GROUP BY label;

-- Why are sessions suspicious?
SELECT primary_reason, COUNT(*) FROM latest WHERE label = 'suspicious' GROUP BY primary_reason;
```

More in [Filtering your data](filtering-your-data.md).

## Changing the rules

The weights live in `WEIGHTS` in `packages/engine/src/analysis.ts`, and the level cut-offs in `LEVEL_CUTOFFS`
in `packages/engine/src/levels.ts`. Change them based on evidence: run the
[evaluation](evaluation.md) on labelled sessions, look at *Why humans weren't confirmed*, and re-score a stored run
before deploying. If you change a number, update this page too.
